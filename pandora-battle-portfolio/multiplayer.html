해결하려던 문제

각 클라이언트가 장비나 인벤토리를 독립적으로 변경하면 플레이어마다 서로 다른 상태를 볼 수 있습니다. 요청을 받는 경로, 권한을 가진 상태, 복제 이후 표현을 분리해야 합니다.

로드아웃·인벤토리 상태 흐름

  1. Client Request선택한 로드아웃 변경 요청
  2. Server권한을 확인하고 상태 변경
  3. Replication변경된 프로퍼티·배열 항목 전달
  4. Client UI복제 콜백으로 표현 갱신

클라이언트 입력과 서버의 상태 변경

로드아웃 선택은 ServerSelectLoadout RPC로 전달합니다. 실제 상태 적용 경로에서 PlayerState와 권한을 확인하고, 인벤토리 변경 또한 서버 권한 아래 수행하도록 구성했습니다.

배열 데이터와 표시용 객체의 구분

인벤토리는 복제 엔트리의 ItemId, 정의 데이터, 수량과 강화 레벨을 바탕으로 클라이언트의 ItemInstance를 구성합니다. 추가·변경·삭제 콜백에서 로컬 목록과 필터를 갱신하며, 수신 완료 시 UI 변경 알림을 정리합니다.

연결과 경기 흐름을 별도 계층으로

OnlineSessionsSubsystem은 방 생성·검색·참가를 담당합니다. 로비와 매치 진행은 별도의 Coordinator로 나누어, 네트워크 연결 처리와 게임 규칙이 하나의 UI 클래스에 집중되지 않게 했습니다.

설계의 결과

플레이어의 요청은 서버에서 처리하고, 클라이언트는 복제된 상태를 기준으로 장비와 UI를 갱신하는 흐름을 만들었습니다.
